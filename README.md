# RAG Access Guard

Исследовательский прототип динамического разграничения доступа к корпоративным знаниям в RAG-системе.

Проект проверяет, что приложение повторно авторизует извлечённые документы и сохранённые ответы с известным происхождением перед передачей модели, выдачей пользователю и последующим чтением.

## Граница защиты

Механизм работает с данными, для которых система сохранила точное происхождение: документ, его неизменяемую версию и фрагмент. Произвольный текст, вручную введённый пользователем, не получает происхождение по смысловому сходству и не относится к этой гарантии.

## Статус

Реализованы базовый FastAPI-сервис и адаптивная оболочка веб-приложения.
Интерфейс содержит разделы `Чат`, `Документы`, `Доступ` и `Аудит`; предметные
операции в них появятся на следующих этапах.

Добавлена схема пользователей, сессий, ролей, документов, прямых и ролевых
разрешений, ревизии политики и аудита. Сессии хранят только хеши токенов;
аудит — идентификаторы и коды событий без содержимого документов.
Реализован серверный вход по паролю Argon2id, восстановление сессии, CSRF
и выход с атомарным отзывом. Прямые и ролевые разрешения управляются через API;
признак администратора не даёт доступ к содержимому документов.

Независимый Python-пакет `rag_access_guard` предоставляет `Guard.authorize_read`:
он проверяет полный набор ссылок на источники по одной согласованной политике,
отказывает при неизвестном происхождении, противоречивом решении или сбое адаптера.
Пакет не зависит от API, базы данных или модели. Аутентификация пользователя,
расчёт разрешений и транзакционная выдача остаются обязанностью приложения.
Адаптер БД и генерация ответов пока не подключены.

Административный реестр принимает `.txt` и `.md` до 10 MiB в UTF-8. Исходные байты,
канонический текст и их SHA-256 сохраняются в неизменяемой версии со статусом
`ready`. Текст разбивается на точные фрагменты до 400 токенов E5 с целевым
перекрытием 50; сохраняются смещения, хеши и принадлежность неизменяемой версии.
Загрузка не создаёт разрешений на чтение; API реестра возвращает только
метаданные. Изменение документа, ревизии политики и аудита выполняется атомарно.

Сборка отдельного пакета: `uv build --package rag-access-guard`.

Сервис предоставляет две проверки состояния:

```text
GET /api/health/live
GET /api/health/ready
```

`live` подтверждает работу процесса. `ready` возвращает успешный ответ только
для PostgreSQL 18 с pgvector 0.8.6 и актуальной ревизией Alembic.

Успешный ответ:

```json
{"status":"ok"}
```

## Локальный запуск API

Требуются `uv` и Docker Desktop в режиме Linux-контейнеров. Версия Python
3.13.15 закреплена в `.python-version`, зависимости проекта — в `uv.lock`.

Локальные значения из `.env.example` предназначены только для разработки.

```powershell
Copy-Item .env.example .env
uv sync --frozen
& "$env:ProgramFiles\Git\bin\bash.exe" scripts/provision-model.sh
docker compose up --detach --wait postgres
$env:RAG_ACCESS_GUARD_AUTH_LIMIT_SECRET = uv run python -c "import secrets; print(secrets.token_hex(32))"
$env:RAG_ACCESS_GUARD_AUTH_ORIGIN = "http://localhost:5173"
$env:RAG_ACCESS_GUARD_LOOPBACK_DEVELOPMENT = "true"
uv run --env-file .env alembic -c apps/api/alembic.ini upgrade head
uv run --env-file .env rag-access-guard-api
```

Для provisioning на Windows нужен Git Bash. Скрипт скачивает tokenizer, конфигурацию
и веса safetensors (около 471 MB) локальной модели
`intfloat/multilingual-e5-small` ревизии `614241f622f53c4eeff9890bdc4f31cfecc418b3`
и проверяет SHA-256 каждого файла. Кеш `.cache/e5/` не входит в Git. Другой каталог
модели задаётся через `RAG_ACCESS_GUARD_MODEL_PATH`; при его изменении задайте также
`RAG_ACCESS_GUARD_TOKENIZER_PATH` на `tokenizer.json` из того же каталога.
Запросы API ничего не скачивают. Вычисление выполняется на CPU вне цикла событий
и блокировки политики. Поиск и генерация ответов пока не подключены.

После запуска:

```powershell
Invoke-RestMethod http://127.0.0.1:8000/api/health/live
Invoke-RestMethod http://127.0.0.1:8000/api/health/ready
```

`RAG_ACCESS_GUARD_AUTH_LIMIT_SECRET` — обязательный приватный секрет оператора:
32 случайных байта в виде 64 hex-символов. Команда выше создаёт его для текущего
локального запуска; для нескольких процессов используется одно сохранённое
значение из приватной конфигурации. Не публикуйте его и не добавляйте в Git.
Тесты используют отдельный случайный synthetic secret.

По умолчанию auth требует HTTPS и использует cookies `__Host-rag_session`,
`__Host-rag_preauth`, `__Host-rag_csrf`: `Secure; SameSite=Lax; Path=/`, без
Domain; первые две — HttpOnly. Явный loopback development mode разрешает только
HTTP origin на localhost или числовом loopback и loopback bind host. Он использует
отдельные cookies `rag_session_local`, `rag_preauth_local`, `rag_csrf_local` без
Secure. Origin задаётся точно, включая порт; wildcard и `null` не разрешены.
Встроенный сервер не доверяет proxy headers и слушает `127.0.0.1` по умолчанию
(`RAG_ACCESS_GUARD_BIND_HOST`). Для браузерного API используйте same-origin proxy;
чужие credentialed CORS origins не разрешены. Веб-форма входа пока не добавлена.

## Пользователи и сессии

Первого пользователя создаёт доверенный локальный оператор:

```powershell
uv run --env-file .env rag-access-guard-create-user --login reader --display-name "Reader"
uv run --env-file .env rag-access-guard-create-user --help
```

Пароль и подтверждение вводятся через скрытый prompt; флагов или переменных
окружения для пароля нет. Минимум 8 символов, максимум 1024 UTF-8 байта;
пробелы и регистр пароля сохраняются. `--admin` даёт административный признак,
но не document grants. Повторный login не перезаписывает пользователя.

Протокол: `GET /api/auth/csrf` → `POST /api/auth/login` с JSON `{login,password}`,
точным `Origin` и `X-CSRF-Token` → `GET /api/auth/me`. Bootstrap устанавливает
одноразовый pre-auth challenge на 10 минут; после login выдаются новая сессия
и новый CSRF. При reload `/me` → `/csrf` восстанавливают личность и сохраняют
здоровый CSRF между вкладками. `POST /api/auth/logout` отправляется без тела
с Origin и CSRF; он отзывает сессию и удаляет cookies. Все auth ответы — no-store.

Сессия действует максимум 8 часов и истекает после 30 минут бездействия;
каждый gate повторно проверяет пользователя и серверное время. В БД хранятся
только SHA-256 digests высокоэнтропийных токенов. Login ограничен 20 попытками
на socket IP и 5 на пару IP/нормализованный login за 10 минут; bootstrap —
20 на IP и 1000 неистёкших challenges глобально. Отказ — одинаковый 429 с
Retry-After. Это локальная DB-защита прототипа; доверие reverse proxy и внешнее
развёртывание требуют отдельной настройки.

## Управление пользователями и аудит

Администратор может изменить `is_active` и/или `is_admin` пользователя запросом
`PATCH /api/admin/users/{id}` и отозвать конкретную сессию через
`DELETE /api/admin/users/{user_id}/sessions/{session_id}`. Нужны Origin и CSRF.
Пустой PATCH и `null` отклоняются; неизменившиеся флаги и повторный отзыв сессии
не повышают ревизию. Самоблокировка разрешена: следующий запрос возвращает `401`;
после снятия административного признака административные операции возвращают `403`.

`GET /api/admin/audit` доступен только действующему администратору. Поддерживаются
фильтры `event_type`, `stage`, `outcome`, `since` (включительно), `until` (исключительно),
`limit` от 1 до 100 (по умолчанию 50) и непрозрачный `cursor` следующей страницы.
Время задаётся в ISO 8601 с часовым поясом; порядок — время и UUID по убыванию.
Каждая страница заново проверяет права. В ответе только идентификаторы, коды,
ревизия и число источников, без названий и содержимого документов.

Изменения политики сериализуются общей блокировкой PostgreSQL. Чтение, получившее
блокировку после commit отзыва, использует новые права. Если разрешённое чтение
завершило свой gate первым, его ответ может физически прийти после отзыва.
Отсутствующая или повреждённая политика и сбой БД дают `503`, а не разрешение
из кеша. Ревизия, изменение и аудит фиксируются или откатываются вместе.

## Реестр документов

После входа с административной учётной записью доступны:

```text
POST  /api/admin/documents                 multipart: title, file
GET   /api/admin/documents
PATCH /api/admin/documents/{id}            JSON: title и/или is_active
GET   /api/admin/documents/{id}/versions
POST  /api/admin/documents/{id}/versions    multipart: file
```

Для `.txt` нужен MIME `text/plain`, для `.md` — `text/markdown` или `text/plain`.
Markdown сохраняется как исходный текст, без выполнения или преобразования HTML. BOM удаляется
только из извлечённого текста, CRLF и CR заменяются на LF; исходные байты сохраняются
без изменений. Неверный UTF-8, управляющие байты и пустой текст отклоняются. Имя файла
не используется как путь хранения; `..`, разделители пути и NUL в нём запрещены.
Размер проверяется по фактическим байтам: файл до 10 MiB, всё тело запроса до
10 MiB + 16 KiB на multipart-обрамление, в том числе без `Content-Length`.

Каждая загрузка создаёт новую неизменяемую версию, даже при одинаковых байтах.
Манифест связывает SHA-256 исходных байтов и текста, размер и конфигурацию парсера;
новые версии также фиксируют конфигурацию разбиения, tokenizer и модель эмбеддингов.
Разбор и вычисление векторов выполняются до блокировки
политики; перед записью заново проверяются сессия, административные права и CSRF.
Новая версия атомарно становится текущей, старый URL возвращает `404`, разрешения
на логический документ сохраняются. Загрузка в неактивный документ отклоняется.
Откат миграции на прежний формат запрещён, если версии уже несовместимы с ним.

Каждому фрагменту соответствует неизменяемый нормализованный вектор из 384 чисел.
E5 получает префиксы `passage: ` и `query: `; mean pooling исключает padding.
Вход длиннее 512 токенов вместе с префиксом и специальными токенами отклоняется,
а не обрезается. Версия становится `ready` только с полным набором векторов.
Ошибка индексации возвращает `503 Indexing unavailable`, сохраняя прежнюю активную
версию. При конкурирующей активации возвращается `409 Version activation conflict`:
готовая проигравшая версия остаётся неактивной. Повторная обработка создаёт новую
версию; исходные байты, фрагменты и векторы старой не перезаписываются.

Изменяющие запросы требуют точный `Origin` и действующий `X-CSRF-Token`.
Каждый запрос заново проверяет сессию и административный признак; ответы реестра
возвращаются с `Cache-Control: private, no-store` и `Vary: Cookie`.
Повторный PATCH с теми же значениями не меняет ревизию.

## Доступ к документам

Администратор выбирает пользователя или роль и управляет разрешениями:

```text
GET    /api/admin/users
GET    /api/admin/documents/{id}/grants
POST   /api/admin/documents/{id}/grants             JSON: user_id или role_id
DELETE /api/admin/documents/{id}/grants/{grant_id}
```

Повторная выдача того же разрешения возвращает `409`, повторный отзыв — `404`.
Эти отказы не меняют ревизию. Успешное изменение разрешения, ревизии и аудита
фиксируется одной транзакцией. POST и DELETE требуют Origin и CSRF.

В запросе выдачи указывается ровно один получатель: `user_id` или `role_id`.
Оба поля одновременно и отсутствие получателя возвращают `422`.

Управление ролями и их составом:

```text
GET    /api/admin/roles
POST   /api/admin/roles                            JSON: code, display_name
PATCH  /api/admin/roles/{id}                        JSON: display_name
GET    /api/admin/roles/{id}/members
PUT    /api/admin/roles/{id}/members/{user_id}
DELETE /api/admin/roles/{id}/members/{user_id}
```

Код роли неизменяем: 1–64 символа, строчные латинские буквы, цифры и `_`,
первый символ — буква. Повтор кода возвращает `409`. Название содержит
1–200 символов после удаления крайних пробелов. Смена названия, состава роли
и ролевого разрешения атомарно меняет ревизию и аудит. Повторные PUT/DELETE
членства возвращают `204`, не меняя ревизию; неизвестная роль или пользователь —
`404`. Название роли, в том числе `admin`, не даёт административных полномочий.
Вложенные роли и явные запреты не поддерживаются.

Для текущей сессии доступны:

```text
GET /api/documents
GET /api/documents/{id}/versions/{version_id}/text
```

Список и чтение используют одну проверку: активный пользователь, активный документ,
его текущая сохранённая версия и хотя бы одно действующее прямое или ролевое
разрешение. Разрешения объединяются: отзыв членства в одной роли не отменяет
независимое прямое разрешение или разрешение через другую роль. Авторство документа
и административный признак не заменяют разрешение.

Каждое чтение повторно проверяется под общей блокировкой политики. После отзыва
последнего разрешения прежний URL возвращает тот же `404`, что неизвестный объект;
название исчезает из пользовательского списка. Чужая и неактивная версия также
недоступны. Ответы возвращаются с `Cache-Control: private, no-store` и `Vary: Cookie`.
Уже доставленные клиенту данные удалить таким способом нельзя.

`/text` выдаёт канонический текст версии реестра, а не источник RAG-ответа:
chunks, ссылки на них и история чата пока не подключены.

## Локальный запуск интерфейса

Требуются Node.js 24.21.0 и npm 11.19.0. Их точные версии закреплены в
`.node-version` и `apps/web/package.json`.

```powershell
Set-Location apps/web
npm ci
npm run dev
```
